# 架构与演进

> 理解系统的总体架构与演进路线，才能判断「二开」和「架构演进」的边界。本节是整本标准的收尾与指引。

## 1. 总体架构

```
┌─────────────────────────────────────────────┐
│  前端（Vue3 + Vite）→ Nginx 静态托管          │
└──────────────────┬──────────────────────────┘
                   │ REST /api（JWT / API Key）
┌──────────────────▼──────────────────────────┐
│  后端（Node.js + Express）                    │
│  ├─ controllers ── services ── models        │
│  ├─ 中间件：auth / audit / dataScope / validate│
│  ├─ 事件总线 eventBus（解耦）                  │
│  ├─ 规则引擎 + 自动化调度                      │
│  ├─ 集成层 integrations/（外部对接适配器）      │
│  └─ 插件注册表 ModuleRegistry                 │
└──────────────────┬──────────────────────────┘
                   │ Sequelize
┌──────────────────▼──────────────────────────┐
│  数据库（默认 SQLite，可选 PostgreSQL）        │
└─────────────────────────────────────────────┘
```

## 2. 核心设计原则

- **订单是中枢，状态是派生的**：订单状态由子模块数据推导，二开不另搞状态逻辑（见 [核心概念](/guide/concepts)）
- **配置 > 代码**：能配置的（字段/规则/流程/模板/报表）不写代码
- **扩展点不动核心**：事件 / 适配器 / 插件，避免改核心文件
- **新增不覆盖**：二开产物放 `modules/<插件>/`，升级不冲突

## 3. 演进路线

系统按四期演进，当前处于「安全开源 → 二开基座」阶段：

| 阶段 | 内容 | 状态 |
|------|------|------|
| 一期 | 安全基线（JWT/限流/审计/脱敏）、数据库稳定性 | 已过 |
| 二期 | 二开基座：自定义字段 / 事件总线 / 规则引擎 / 流程配置 / 插件协议 | 已落地 |
| 三期 | OPC 体验：一键部署、备份恢复、打印模板、报表 | 已落地 |
| 四期 | 生态：Monorepo 物理拆分、双授权、全量开源 | 规划中 |

## 4. 可扩展性体现在哪

- **插件化**：`ModuleRegistry` 协议，一个目录 = 一个模块，可启停（见 [插件协议](/dev/plugins)）
- **配置化**：自定义字段 / 业务规则 / 流程 / 模板 / 报表，全部 Web UI 可配
- **事件驱动**：领域事件可被订阅，解耦挂接（见 [事件订阅](/dev/events)）
- **适配器层**：外部系统对接统一接口，自动发现（见 [外部对接适配器](/dev/adapters)）
- **数据层**：模型统一走 Sequelize，SQLite 与 PostgreSQL 可切换

## 5. 演进边界：二开 vs 架构演进

| 你的改动 | 归类 | 注意 |
|----------|------|------|
| 加字段 / 加规则 / 加模板 / 加报表 | 二开（配置） | 无需动核心 |
| 加模块 / 加适配器 / 订阅事件 | 二开（代码） | 走扩展点，不改核心 |
| 改状态机默认逻辑 / 改派生逻辑 | 需谨慎 | 先读 `orderController` 的派生函数 |
| Monorepo 拆分 / 授权 / 开源 | 架构演进 | 遵循开源方案，不单点落地 |

## 6. 数据层演进

- **默认 SQLite**：单用户/单机，零运维
- **切 PostgreSQL**：多团队并发、JSONB 索引、高可用要求时
- 迁移：`backend/migrations/` 增量迁移，两种库通用（见 [数据库迁移](/dev/migration)）
- 决策参考：量大、并发高、需要更强查询能力 → PostgreSQL

## 7. 标准如何演进

本标准本身也应随系统演进而更新：

- 新增扩展点 → 在「扩展点体系」补充章节
- 新增工程约束 → 在「工程规范」补充，并更新 [纪律与最佳实践](/dev/best-practices)
- 架构变化 → 更新本节与 [核心概念](/guide/concepts)

> 标准是活的。任何「系统中做了但文档没写」的扩展点，都应回填到本 wiki，保持标准与代码一致。
