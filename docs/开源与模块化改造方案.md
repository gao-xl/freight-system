# 开源与模块化改造方案

> 版本：v1.0
> 目标：将单体货代系统改造为 **「核心框架 + 可插拔业务插件」的 Monorepo**，并开源
> 决策（已确认）：开源授权=**双授权**；模块粒度=**核心框架+业务插件**；仓库形态=**Monorepo + npm workspaces**；开源范围=**全量开源**

---

## 1. 目标与收益

### 1.1 改造目标
1. **框架可复用**：把通用能力（用户/权限/客户/订单主数据/打印引擎/对接层/定时任务）提炼为 `core`，可被其他项目复用。
2. **模块可插拔**：报关/财务/港口/青岛港等作为独立插件，按需启用，互不硬依赖。
3. **开源可协作**：Monorepo 统一管理，一套 CI、统一版本，社区易参与。

### 1.2 收益
- 降低二次开发门槛，吸引社区贡献。
- 增值模块可商业授权，形成可持续的开源商业模式。
- 模块边界清晰，单一模块升级/替换不影响整体。

---

## 2. 双授权策略（全量开源 + 许可矩阵）

> 全量开源 = 代码全部公开可见；双授权 = 通过 **许可证分层** 保障核心框架自由使用、增值模块商业价值。

| 层级 | 内容 | 授权 | 说明 |
|------|------|------|------|
| **核心框架** | auth/RBAC、用户、组织、客户/供应商基础、订单主数据、通用 CRUD、打印模板引擎、对接适配层、定时任务、前端框架 | **MIT** | 自由使用/修改/商用 |
| **基础模块** | 订单、订舱、单证基础 | **MIT** | 随核心开源 |
| **增值模块** | 报关对接、财务结算、港口/青岛港专项、EDI、客户自助门户、AIS 船舶追踪 | **商业授权 / LGPL** | 源码公开，商用需授权或遵循 LGPL 强约束 |

> 实现方式：仓库内 `LICENSE` 为 MIT，各 `packages/*` 包内声明自身 `license` 字段；增值模块加 `NOTICE` 说明商用需授权。

## 4. 核心框架 `packages/core`

### 4.1 职责
- **基础能力**：数据库初始化、配置、鉴权、RBAC、通用响应/分页/编号。
- **扩展机制**：`ModuleRegistry`（后端模块注册）、`RouteRegistry` + `MenuRegistry`（前端路由/菜单注册）。
- **公共服务**：打印引擎、对接适配层、定时任务调度。

### 4.2 模块注册协议（后端）
每个业务插件导出统一协议，核心框架自动加载：
```js
// packages/modules/module-order/index.js
module.exports = {
  name: 'order',
  title: '订单管理',
  models: [Order, OrderContainer],          // 数据模型
  routes: (router, { authRequired, requirePermission }) => { ... }, // 路由挂载
  services: { orderService },
  seed: async () => { ... },                // 可选初始化
  menu: { path: '/orders', icon: 'Document', permission: 'order:read' },
};
```
`ModuleRegistry.load(modules)` 遍历并收集 models（注册到 sequelize）、挂载 routes、登记菜单。

### 4.3 模块依赖与加载顺序
- 核心先加载 db + auth + 基础模型（User/Customer/Supplier）。
- 业务模块按声明的 `dependencies` 排序加载，避免关联缺失。

## 5. 前端模块化

### 5.1 路由/菜单动态注册
- 核心框架提供 `registerModule(module)`，模块声明 `routes` + `menu`。
- `apps/web/src/main.js` 启动时加载核心 + 各模块，动态合并路由与左侧菜单。
- 菜单按权限过滤（复用现有 `MainLayout` 的 `hasPermission`）。

### 5.2 前端包划分
| 包 | 内容 |
|----|------|
| `@ff/ui` | Element Plus 封装、通用表格/表单/统计卡片组件 |
| `@ff/router` | 路由与菜单注册机制 |
| `@ff/api` | Axios 封装 + 各模块 API 定义 |
| `apps/web` | 组装入口、布局、登录 |

## 8. 改造实施步骤

### 阶段 1：Monorepo 骨架
1. 根 `package.json` 配置 `workspaces: ["apps/*", "packages/*", "packages/modules/*"]`。
2. 用 `git init` 初始化仓库，补 `LICENSE`、`.gitignore`、`.env.example`。
3. 迁移目录：`backend/src` → `apps/api` + `packages/core`；`frontend/src` → `apps/web` + `packages/ui/router/api`。

### 阶段 2：核心框架抽取
1. 抽取 `db/config/utils/middleware` 到 `packages/core`。
2. 实现 `ModuleRegistry`（后端）+ `RouteRegistry/MenuRegistry`（前端）。
3. 打印引擎、对接适配层、定时任务迁入 core。

### 阶段 3：业务模块切片
1. 按拆分清单把现有 controllers/models/routes 迁入各 `module-*`。
2. 每个模块实现统一注册协议，`apps/api` 仅做组装。
3. 前端各页面迁入对应模块，路由/菜单动态注册。

### 阶段 4：开源完善
1. 重写 README、补 CONTRIBUTING、CI。
2. 补核心测试，跑通 `npm run build` 与 `npm start`。
3. 首次提交并推送 GitHub。

### 阶段 5：增值模块授权
1. 为 module-port/module-customs/module-finance 加双授权声明。
2. 建立商业授权说明文档。

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| 模块间隐性耦合 | 严格依赖声明 + 统一注册协议，逐步解耦 |
| SQLite 数据迁移 | 已完成：沿用 Sequelize 模型迁移至 PostgreSQL，系统 PostgreSQL-only |
| 前端动态路由复杂度 | 先用"静态路由 + 模块化菜单"过渡，再推进全动态 |
| 开源泄敏 | .gitignore 排除 db/密钥/上传文件，密钥走环境变量 |
| 商业模块被滥用 | 双授权 + NOTICE，明确商用需授权 |
