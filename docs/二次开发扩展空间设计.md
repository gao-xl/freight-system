# 二次开发扩展空间设计

> 版本：v1.0
> 定位：为**货代公司定制化**预留系统化扩展点，让"核心框架 + 公司定制"可分离：核心升级不破坏定制、定制不污染核心。
> 关联：承接《开源与模块化改造方案.md》（Monorepo 插件化）；延伸《控制性设计手册.md》《打印模板设计功能方案.md》。
> 核心原则：**核心可升级、定制可插拔、配置优先于代码**。

---

## 1. 现状扩展点盘点

| 能力 | 现状 | 能否支撑公司定制 |
|------|------|------------------|
| 外部对接适配层 | ✅ `integrations/adapters/`（port/customs/finance） | 公司对接特色服务商可扩展 |

| 定时任务 | ✅ node-cron | 公司特色提醒/轮询 |
| 模块化插件 | 📋 设计阶段（Monorepo） | 待落地 |
| **自定义字段** | ❌ 无 | **未预留** |
| **流程/状态机配置** | ❌ 状态写死 ENUM | **未预留** |
| **规则引擎** | ❌ 无 | **未预留** |
| **事件/钩子机制** | ❌ 无 | **未预留** |
| **报表自定义** | ❌ 固定接口 | **未预留** |

> 结论：系统已能"配置"，但缺"**公司业务语义层**"的扩展点。下面补齐。

## 2. 六大扩展点设计

### 2.1 自定义字段（Custom Fields）——最常见定制需求
公司要给订单/客户加"指定货代""付款条款""特殊要求"等字段，**不改代码**。

```js
// CustomField 表
{
  id, 
  bizType: 'order',            // 绑定业务类型：order/customer/booking/finance
  fieldKey: 'custom_agent',    // 字段标识
  label: '指定货代',
  fieldType: 'string',         // string/number/date/enum/bool
  options: '["青岛班轮","上海外运"]',  // enum 的可选项
  required: false,
  isList: false,               // 是否进列表/搜索
  enabled: true,
  sort: 10,
}
```
- **存储**：推荐 `JSONB` 列（PostgreSQL）存 `customFields`，或独立 `custom_field_value` 表。
- **通用接口**：`GET/PUT /{biz}/custom-fields` 增删改字段定义；业务实体的 `customFields` 一并读写。
- **前端**：根据 `fieldType` 动态渲染表单控件，无需改页面。

### 2.2 流程/状态机配置化（Workflow）
货代订单状态不再是写死 ENUM，而是**可配置的节点流转**。

```js
// WorkflowConfig 表
{
  id, bizType: 'order',
  status: 'booking',          // 当前状态
  nextStatus: 'confirmed',    // 可流转到
  action: 'confirm',          // 触发动作
  fromRole: 'operator',       // 谁可触发（RBAC 权限点）
  auto: false,                // 是否自动流转
}
```
- 列表/详情按配置渲染"当前状态可达的下一动作"。
- 状态变更走统一 `transition` 接口，触发校验 + 审计 + 事件。

### 2.3 规则引擎（Rules）
把"业务规则"从代码抽出为**可配置规则**，如：报价毛利过低预警、信用额度超限拦截、青岛港特定场站必填字段。

```js
// BusinessRule 表
{
  id, name: '毛利预警',
  bizType: 'quotation',
  trigger: 'onSave',          // onSave/onSubmit/onTransition/定时
  condition: JSON,            // { field:'grossMargin', op:'<', value:0.1 }
  action: 'block' | 'warn' | 'notify',
  message: '毛利率低于 10%',
  enabled: true,
}
```
- 条件可用 JSON 表达式或简单表达式字符串（如 `table.field op value`）。
- 二期可升级为轻量表达式引擎，避免引入沉重规则引擎依赖。

### 2.4 事件/钩子机制（Hooks/Events）
跨模块解耦与公司定制挂载点：订单创建后通知、对账后生成账单、船期变更发提醒。

```js
// 事件广播（core/events）
events.emit('order.created', { orderId, ... });

// 公司定制监听（不侵入核心）
events.on('order.created', async (payload) => {
  // 对接公司自己的 OA/企业微信/邮件
  await companyIntegrator.push(payload);
});
```
- 事件清单：`order.created/updated/transitioned`、`quotation.confirmed`、`finance.billed`、`booking.scheduled` 等。
- 事件总线与《控制性设计手册》的定时任务/日志打通。

### 2.5 报表自定义（Reports）
公司特色统计/对账报表，不写死后端接口。

- **方案**：报表定义（SQL/JSON 查询 + 列配置）+ 通用报表执行接口。
- 二开人员只需维护"报表定义"，前端通用表格/图表渲染。
- 与现有 ECharts 看板复用渲染层。

### 2.6 模块/插件化（Module Plugins）
见《开源与模块化改造方案.md》的 `ModuleRegistry` 协议。公司定制优先写成**独立插件**：
```js
module.exports = {
  name: 'company-xxx',
  models, routes, services, seed, menu,
  events,        // 订阅核心事件（2.4）
  customFields,  // 注册自定义字段定义（2.1）
  rules,         // 注册业务规则（2.3）
};
```

## 3. 扩展点优先级

| 优先级 | 扩展点 | 价值 | 批次 |
|--------|--------|------|------|
| P0 | 自定义字段 | 覆盖 80% 的公司定制诉求 | 批次 A |
| P0 | 事件/钩子 | 解耦 + 对接公司系统 | 批次 A |
| P1 | 流程状态机配置 | 适配公司操作流程 | 批次 B |
| P1 | 业务规则引擎 | 预警/校验灵活化 | 批次 B |
| P2 | 报表自定义 | 特色统计 | 批次 C |
| P2 | 模块插件化 | 完整二开形态 | 跟随《开源方案》 |

## 4. 落地批次

### 批次 A（立即）
- 新增 `CustomField` 模型 + 通用接口 + 前端动态表单渲染。
- 新增 `EventBus`（core/events）+ 事件清单 + 日志埋点。

### 批次 B（上线前）
- `WorkflowConfig` 状态机配置化，订单状态改走 transition。
- `BusinessRule` 规则引擎（onSave/onSubmit 触发）。

### 批次 C（二期）
- 报表定义 + 通用报表执行。
- 自定义字段/规则/事件纳入 `ModuleRegistry` 插件协议，与开源方案合并。

## 5. 对现有代码的影响（最小化侵入）

| 文件 | 改动 |
|------|------|
| `models/` | 新增 CustomField / WorkflowConfig / BusinessRule；业务模型加 `customFields`(JSON) |
| `core/events`（新增） | 事件总线 |
| `baseController.js` | 通用 CRUD 支持 `customFields` 透传 + 触发事件 |
| `services/` | 新增 customFieldService / workflowService / ruleService |
| `routes/index.js` | 挂载通用扩展接口 |
| 前端 | 新增"自定义字段管理"页 + 动态表单控件组件 |

## 6. 验收标准

- [ ] 新增自定义字段后，订单/客户表单动态渲染且可存储、可搜索
- [ ] 订单状态流转可配置，操作走权限校验 + 审计
- [ ] 业务规则可配置触发与拦截/预警
- [ ] 核心事件可被公司插件订阅，且不修改核心代码
- [ ] 新增公司定制插件可独立启用/卸载
- [ ] 核心升级不影响已配置的定制项

---

## 7. 与开源方案的关系

本设计是《开源与模块化改造方案.md》的**定制化语义层**：Monorepo 解决"代码怎么拆"，本设计解决"**公司业务怎么配**"。二者在批次 C 合并——自定义字段/规则/报表/事件全部纳入插件协议，形成"核心框架 + 配置化定制 + 公司插件"的完整二开体系。
