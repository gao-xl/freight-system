# 货代管理系统数据库稳定性改造方案

> 版本：v1.0
> 目标：将系统从内置 SQLite 迁移至 **PostgreSQL**，并调整为**多服务器/上云**部署架构，从根本上解决数据存储的稳定性、并发与安全问题。

---

## 1. 背景与问题

系统当前使用 **SQLite**（通过 Sequelize ORM 连接本地文件 `data/freight.db`）。SQLite 是嵌入式单文件数据库，存在以下不适用于生产环境的问题：

| 问题 | 表现 | 影响 |
|------|------|------|
| 并发写入差 | 多用户同时操作时锁库、卡顿、报错 | 多岗位同时录单/改单体验差 |
| 无网络访问 | 只能本机进程访问 | 无法多终端/多服务器部署 |
| 无账号权限 | 无数据库级角色/权限体系 | 安全薄弱 |
| 单点风险 | 文件损坏即丢数据，无主从/备份 | 数据安全无保障 |
| 扩展瓶颈 | 数据增长后 IO 与稳定性受限 | 无法支撑长期业务积累 |

**结论**：SQLite 仅适合开发/演示，不能满足中小企业货代日常运营的稳定性要求，必须迁移。

---

## 2. 目标架构

```
                         ┌─────────────────────────────┐
                         │          客户端浏览器          │
                         │  (运营/财务/管理/客户门户)      │
                         └──────────────┬──────────────┘
                                        │  HTTPS
                         ┌──────────────▼──────────────┐
                         │    Node.js 应用服务 (无状态)    │
                         │          Express + Sequelize   │
                         └──────────────┬──────────────┘
                                        │  TCP 5432
                         ┌──────────────▼──────────────┐
                         │       PostgreSQL 主库         │
                         │   (连接池 / 备份 / 主从可选)   │
                         └─────────────────────────────┘
```

**架构要点**
- **应用无状态化**：JWT 已实现无状态鉴权（无需 Session），可水平扩展多实例。
- **数据库独立部署**：PostgreSQL 与应用服务分离，支持独立备份、扩容、高可用。
- **连接池**：应用侧通过 Sequelize 连接池管理数据库连接。

---

## 3. 数据库选型

**选定 PostgreSQL** 理由：

- 功能强、稳定性好，支持复杂查询、JSON、事务、行级锁。
- 高并发写能力远超 SQLite，适合多用户协同。
- 开源免费，多服务器/上云部署生态成熟（云厂商均有托管实例）。
- 当前代码全部走 Sequelize ORM，**切换成本极低**。

数据表（由 Sequelize 模型自动生成，共 10 张）：
`User / Customer / Supplier / Order / Booking / CustomsDeclaration / Document / ShipmentTrack / FinanceRecord / IntegrationConfig`

## 4. 代码改造方案

### 4.1 依赖调整（`package.json`）

```json
{
  "dependencies": {
    "bcryptjs": "^2.4.3",
    "cors": "^2.8.5",
    "dotenv": "^16.4.5",
    "express": "^4.19.2",

    "pg": "^8.12.0",

    "uuid": "^9.0.1"
  }
}
```

- **移除** `sqlite3`（不再使用）。
- **新增** `pg`（PostgreSQL 官方驱动，Sequelize 适配）。

### 4.2 配置改造（`src/config/index.js`）

```js
require('dotenv').config();

module.exports = {
  port: process.env.PORT || 3000,
  jwtSecret: process.env.JWT_SECRET || 'freight-sys-dev-secret-2026',
  jwtExpiresIn: '12h',
  db: {
    host: process.env.DB_HOST || 'localhost',
    port: parseInt(process.env.DB_PORT || '5432', 10),
    database: process.env.DB_NAME || 'freight',
    username: process.env.DB_USER || 'freight',
    password: process.env.DB_PASSWORD || '',
    dialect: 'postgres',
    logging: false,
    pool: {
      max: process.env.DB_POOL_MAX ? parseInt(process.env.DB_POOL_MAX, 10) : 10,
      min: 0,
      acquire: 30000,
      idle: 10000,
    },
    dialectOptions: {
      // 云 RDS 若要求 SSL，开启此项
      ssl: process.env.DB_SSL === 'true' ? { rejectUnauthorized: false } : false,
    },
  },
  // 外部系统对接配置（端口/海关/财务等），可在运行期通过 IntegrationConfig 表动态维护
  integrations: {
    port: process.env.PORT_SVC_URL || 'http://localhost:4001',
    customs: process.env.CUSTOMS_SVC_URL || 'http://localhost:4002',
    finance: process.env.FINANCE_SVC_URL || 'http://localhost:4003',
  },
};
```

### 4.3 连接层改造（`src/db/index.js`）

```js
const { Sequelize } = require('sequelize');
const config = require('../config');

const sequelize = new Sequelize(
  config.db.database,
  config.db.username,
  config.db.password,
  {
    host: config.db.host,
    port: config.db.port,
    dialect: 'postgres',
    logging: config.db.logging,
    pool: config.db.pool,
    dialectOptions: config.db.dialectOptions,
    define: {
      underscored: false,
      freezeTableName: false,
    },
  }
);

module.exports = sequelize;
```

> 由于原先 `db/index.js` 中 `path`/`fs` 用于创建 SQLite 数据目录，迁移后不再需要，予以移除。

### 4.4 模型与启动逻辑

- **模型层无需改动**：全部使用 Sequelize 标准 DataTypes（`INTEGER/STRING/ENUM/DECIMAL/DATEONLY/TEXT` 等），PostgreSQL 均原生支持。
- **表结构初始化**：`server.js` 中的 `sequelize.sync()` 与 `seed.js` 中的 `sequelize.sync({ force: true })` 在 PostgreSQL 下同样可用，用于开发/演示环境自动建表。
- **生产环境建议**：改用 Sequelize 迁移（Migrations）管理表结构，避免 `sync` 在正式库上直接改表。

## 5. 部署方案（多服务器 / 上云）

### 5.1 数据库部署（推荐托管实例）

| 云厂商 | 托管服务 |
|--------|----------|
| 阿里云 | RDS PostgreSQL |
| 腾讯云 | TDSQL-C / CloudBase PostgreSQL |
| AWS | RDS for PostgreSQL |

**托管实例优势**：自动备份、主从高可用、监控告警、SSL、安全组，无需自运维。

### 5.2 应用服务部署

- **方式一（推荐）**：打包为 Docker 镜像，部署到云服务器 / 容器服务（ECS/EC2/容器）。
- **方式二**：直接 `node src/server.js`（配合 PM2 守护进程）。

```bash
# 安装依赖
npm install

# 初始化数据库（演示数据）
npm run seed

# 启动
npm start
```

### 5.3 高可用与备份

| 项 | 方案 |
|----|------|
| 主从 | 云 RDS 开启只读实例 / 主备高可用 |
| 备份 | 每日自动全量备份 + 开启 WAL 归档（PITR 时间点恢复） |
| 应用多实例 | 无状态 + 负载均衡（SLB/Nginx），水平扩容 |
| 迁移建库 | 生产用 Sequelize Migration 管理表结构 |

## 6. 迁移步骤（时序）

1. **准备数据库**：在云 RDS 创建 `freight` 库与专用账号（最小权限）。
2. **改配置**：按 §4.2-4.5 更新 `config`、`db/index.js`、`.env`。
3. **装依赖**：`npm install`（安装 `pg`，移除 `sqlite3`）。
4. **验证连通**：启动 `npm start`，确认 `/api/health` 返回 `up`。
5. **初始化数据**：开发环境执行 `npm run seed` 建表并灌入演示数据。
6. **功能回归**：跑通登录、订单、订舱、报关、单证、跟踪、财务、对接等模块。
7. **上线切换**：切换 DNS/负载均衡指向新应用，观察日志与监控。
8. **数据迁移（如有旧数据）**：用 `pgloader` 或编写脚本将 SQLite 导出为 SQL 再导入 PostgreSQL。

## 8. 风险与注意事项

- **SQLite AUTOINCREMENT 语义**：PostgreSQL 用 `SERIAL`/`IDENTITY`，Sequelize 已自动处理，无需干预。
- **ENUM 类型**：PostgreSQL 原生支持 ENUM，Sequelize 会自动建 ENUM 类型，注意同名字段类型需一致。
- **大小写**：PostgreSQL 对未加引号标识符默认小写，Sequelize 已处理，业务无感。
- **时区**：`DATEONLY` 与 `DATE/TIMESTAMP` 在 PostgreSQL 语义略有差异，建议统一用 UTC 存储、展示时做时区转换。
- **同步策略**：生产勿用 `sync({ force:true })`（会删表重建），务必用 Migration。
