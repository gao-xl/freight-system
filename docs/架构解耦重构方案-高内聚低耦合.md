> 版本：v1.0　日期：2026-08-09　状态：待评审

## 0. 执行摘要

本项目已具备优秀的二开基座（ModuleRegistry 协议、eventBus、统一适配器签名、插件样例），但核心业务仍是「controller 直连 model」的两层扁平结构，且已出现 1 处**分层倒置**（服务反向依赖控制器）与 1 处**循环依赖伤疤**（复制代码规避）。本方案给出：

- **现状耦合审查**：🔴 高耦合 6 项 / 🟠 中耦合 8 项 / 🟢 健康 7 项（重构时勿动）
- **目标架构**：务实五层（API → 应用 → 领域 → 数据访问 → 基础设施），依赖方向铁律落地为 lint 规则
- **模块划分**：内核 kernel（8 模块）+ 业务域 domains（12 域）+ 二开扩展点（7 个），插件协议统一到全部业务
- **解耦动作 E1–E10**：每项含 现状/方案/改动文件/风险/验证
- **迁移路径 F0–F5**：每阶段可独立验证、可回滚，不回归现有功能
- **Monorepo 决策**：当前继续逻辑模块化，不执行物理拆分（ADR-002 修订触发条件）

### 1.1 高耦合（必须处理）

| # | 耦合点 | 证据（文件:行号） | 性质 |

### 1.3 健康（好范式，重构时勿动，推广）

1. **ModuleRegistry 协议**（`core/moduleRegistry.js`）：load/mountRoutes 两步分离、拓扑排序、autoMount 控制、单个模块加载失败隔离——二开基座地基，设计正确
2. **eventBus 事件驱动**（`services/eventBus.js`）：跨模块解耦主要手段，事件命名 {module}.{action}
3. **适配器统一签名**（`integrations/adapters/` 12 个）：{code,name,send,query} + IntegrationConfig 表存密钥，无硬编码密钥——外部对接教科书范式
4. **qingdao-port 插件**（`modules/qingdao-port/index.js`）：models+routes+menu+events+services 全协议字段、路由自动挂载——存量业务升级插件的完整范式
5. **前端领域组织意识**：views 按领域目录 + composables 拆分（useImport/usePrintTemplate/useResponsive 等 6 个）+ stores 仅 3 个小 store（非 monolithic）
6. **中间件三层分离**：auth guard / dataScope / validate 职责清晰
7. **数据隔离基础设施通用化**：`dataScope.js` 的 scopedWhere/scopedFindOne/attachOwnership/hasScopeColumns 对任意模型生效，比 baseController 布尔开关更彻底
8. **server.js 装配精炼**：148 行，未直接 import 任何 controller（全走 routes）——注意：装配精炼 ≠ 装配可扩展（见 E10）

| 排名 | 热点 | 涉及文件 | 耦合类型 | 解耦方向 |

## 2. 目标分层架构

当前是 controller 直接操作 model 的两层结构。目标为**务实五层**（不引 DDD 全套，CommonJS 工程、无 DI 容器，务实优先）：

```
┌─────────────────────────────────────────────────────────────┐
│ API 层（routes + controllers）                                │
│ 职责：参数校验(validate) / 权限(guard) / 数据隔离(dataScope)    │
│       / 调 service / 组装 HTTP 响应。禁止任何业务规则与模型查询。 │
├─────────────────────────────────────────────────────────────┤
│ 应用层（application services）                                │
│ 职责：用例编排 / 事务边界 / 跨域调用 / 发射事件                  │
│       订单创建流程、推进节点、生成应收、对账等「用例」。           │
├─────────────────────────────────────────────────────────────┤
│ 领域服务层（domain services / 纯逻辑）                         │
│ 职责：订单状态机、computeReached、deriveOrderStatus、毛利计算。  │
│       纯函数，不 import models、不依赖 req/res。               │
├─────────────────────────────────────────────────────────────┤
│ 数据访问层（repositories / 现为 models 直用）                  │
│ 职责：模型查询封装。MVP 阶段不为每个模型建 repo，                │
│       只为「被多域引用的模型」和「跨域写」建访问门面。           │
├─────────────────────────────────────────────────────────────┤
│ 基础设施层（db / integrations / third-party）                 │
│ 职责：sequelize 连接、外部适配器、文件存储、定时任务调度。        │
└─────────────────────────────────────────────────────────────┘
```

### 依赖方向（铁律，落地为 .eslintrc no-restricted-imports）

- 允许：`routes → controllers → application services → domain + data access → infrastructure`
- 禁止：services/domain 反向 require controllers（现状 `automationService.js:5` 违反）
- 禁止：controllers 直接查 models（现状 `orderController.js:72-76,355-361` 违反）
- 禁止：domain 纯逻辑 import models / req / res
- 禁止：跨域 require 对方 models（现状 `alertService.js:2` / `ruleEngineService.js:18` / `workflowService.js:7` 违反）
- 跨域协作走：对方 service 门面 或 事件总线；跨域写数据只能走事件或对方 service

### 模块地图（目标目录）

```
backend/src/
├── core/                    # 内核：零业务依赖
│   ├── moduleRegistry.js    # 模块注册协议（已有）
│   ├── eventBus.js          # 事件总线（从 services/ 迁入 core/）
│   ├── error.js             # 业务异常类型（带 status 的统一错误出口）
│   ├── config.js            # 配置加载
│   └── serviceLocator.js    # 轻量服务定位器（可选：供插件拿核心服务，替代 require 硬链）
├── kernel/                  # 核心内核模块：平台能力，与货代业务无关
│   ├── auth/  rbac/  data-scope/  audit/  custom-field/
│   ├── workflow/  rule-engine/  notification/
├── domains/                 # 业务域：可独立开发/测试/替换
│   ├── order/  booking/  customs/  customer/  supplier/  document/
│   ├── tracking/  finance/  quotation/  container/  report/  dashboard/
├── integrations/            # 外部系统适配（已有，保持）
├── modules/                 # 插件目录（协议已有，统一后全部走此）
├── routes/                  # 路由权威源（逐步瘦身，插件路由移出）
├── models/                  # 模型定义（保留；新增按域分包，关联收敛）
├── migrations/              # 数据库迁移（21 个，保持，修复重复前缀）
├── db/  utils/  middleware/  validation/
└── server.js                # 入口只装配（挂中间件+挂路由+调 bootstrap.run()）
```

注：domains/ 是**逻辑聚合**（每域目录 = controller+service+domain+model 引用），不是物理拆包；物理拆包见 §7（ADR-002 触发条件）。

## 4. 模块间通信契约

### 4.1 事件清单（现有事件，含 payload 契约）

CRUD 事件（baseController 自动发射，payload={id,data,user}）：

- order.created/updated/deleted/restored
- customer.created/updated/deleted/followed
- supplier.created/updated/deleted
- booking.created/updated/deleted/shipped
- customs.created/updated/deleted
- document.created/updated/deleted/generated
- finance.created/updated/deleted/billed
- quotation.created/updated/deleted/confirmed/converted
- track.created/updated/deleted

领域事件（服务/控制器手动发射）：

- order.transitioned（payload={id,from,to,rule}）
- alert.created/resolved　automation.executed　user.login　qingdao.node_updated（插件声明）

新增建议事件（消除跨域直写）：

- finance.payment_applied（收款核销完成，替代 automationService 直写 FinanceRecord）
- finance.record_created（替代自动化直读财务表做幂等检查，改为订阅维护）
- audit.recorded（审计落库通知，供插件观察）

### 4.2 接口契约（跨域门面签名）

跨域调用只允许 service 门面，禁止直连模型：

- orderService.getById(id) → {id,orderNo,status,type,customerId,...}
- orderService.computeReached(id) → Set（迁出控制器后的纯函数入口）
- financeService.getByOrder(orderId) → FinanceRecord[]（替代各服务直查）
- financeService.createRecord(payload)（替代 automationService 直写）
- auditService.record({module,action,method,targetId,summary})（替代各服务直写 AuditLog）
- dataScope.resolveDataScope(userId) / scopedWhere(req,where)（保持现状签名，不动）
- moduleRegistry.get(name) / list()（插件发现内核，保持）

### 4.3 依赖方向规则（落成 .eslintrc no-restricted-imports）

```
core ← kernel ← domains ← modules(插件)
禁止：services/** → controllers/**    （现状 automationService.js:5 违反）
禁止：controllers/** → models/** 直接查询（现状 orderController.js:72 违反）
禁止：domain/** → models/**（纯逻辑）
禁止：跨域 require('../models').XXX（现状 alertService.js:2 违反）
禁止：domain 之间互相 require（走事件或门面）
```

### 4.4 代码评审红线（禁止规则）

1. 任何 service/domain 出现 `require('../controllers/...')` → 退回
2. 任何非 finance 域出现 FinanceRecord.create/update/destroy → 退回（改走 financeService 或事件）
3. 任何非 audit 域出现 AuditLog.create → 退回（改走 auditService.record）
4. 任何非 order 域出现 Order.findAll({where}) → 退回（改走 orderService 查询门面）
5. routes/index.js 新增「存量业务」端点时若同时改 modules 扁平 js → 退回（必须先协议化）

## 5. 具体解耦重构方案（E1–E10）

> 每项含：现状 → 方案 → 改动文件 → 风险 → 验证。

### E1+E2. 订单域解耦（分层倒置根治 + 领域逻辑下沉，最优先，阻断一切后续）

- **现状**：automationService.js:5 require('../controllers/orderController')；orderController.js 539 行内嵌状态机/推导/推进。

  2. 新建 `domains/order/orderService.js`：承载事务外壳 + 业务用例（推进/批量推进/批量状态/毛利/利润汇总）

- **风险**：advanceOne 的 strict 语义、事务、并发防呆行为必须逐字保持；batchAdvance 失败隔离保持。**关键约定：自动化推进必须传 {strict:false}**（loaded/cleared 跳进依赖此参数）
- **验证**：扩展 regression.js 做「创建订单→推进各节点→断言 derivedStatus 与旧逻辑一致」全流程回归；跑全绿 + 订单详情/推进/批量冒烟

## 7. Monorepo 决策建议（ADR-002 评估）

**结论：当前继续逻辑模块化，不执行物理拆分。ADR-002 保持 Accepted 待触发。**

理由（基于真实代码）：

1. **触发条件未满足**：ADR-002 写明「社区出现第一个想独立发布插件的真实需求 或 v2.0 插件市场」。当前无此信号
2. **逻辑边界尚未统一**：E7 证明 modules/ 还有 13 个扁平 js 未协议化、modules/index.js 是死代码。物理拆分解决「发布边界」，解决不了「逻辑边界」；在逻辑边界未统一时拆分，等于把双轨制固化成包边界，坏边界成本翻倍
3. **分层倒置未解决**：automationService.js:5 反向依赖控制器，在 Monorepo 里会直接变成跨包依赖，拆分时更难修
4. **二开者收益后置**：OPC 小团队核心诉求是「协议统一 + 目录清晰」，逻辑模块化已能满足

**对 ADR-002 的修订建议**：

- 把「模块协议统一到全部业务（modules 双轨制收口）」写入触发条件，与「社区插件需求」并列
- 触发顺序：先完成 F0–F3，再评估物理拆分
- 若社区插件需求出现，按 ADR-002 步骤执行即可（目录边界=包边界 的映射关系已明确）

## 8. 前端解耦方案

- 健康：stores 非 monolithic（仅 auth/onboarding/quotation 三小 store）；views 按领域目录；composables 已拆分
- 问题：api/index.js 277 行上帝模块（E8）；FinanceList.vue 749 / OrderDetail.vue 725 超大组件

### 8.2 store 按领域切分（不过度设计）

- 现状业务状态基本在 view 组件内，符合「局部状态就近」原则，不强行全局化

### 8.3 组件/页面分层

```

composables/             # 逻辑复用（现有 6 个保持）
api/                     # 按域分包（E8）
stores/                  # 按域共享状态
```
