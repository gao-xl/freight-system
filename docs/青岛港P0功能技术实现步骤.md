# 青岛港 P0 刚需功能技术实现步骤

> 版本：v1.0
> 所属项目：《青岛港针对性功能设计.md》P0 部分
> 范围：出口全程节点看板、进港/运抵监控、放行监控、装载舱单检查、集港/截港时间管理
> 说明：本拆解贴合现有代码结构（`backend/src/models`、`controllers/baseController` 工厂、`routes/index.js`、`frontend/src`），给出可执行的分步实现方案，暂不写代码。

---

## 0. 功能依赖关系总览

```
[数据源层] 手动录入 / 场站查询 / 港口EDI / 报关模块
        │
        ▼
[模型层]  QingdaoNode(7节点) + Order/Booking扩展字段 + QingdaoAlertPreview
        │
        ▼
[服务层]  qingdaoService.js
         ├── getNodeBoard(orderId)      → 出口7节点看板汇总
         ├── updateNode(...)            → 手动/自动更新节点
         ├── checkManifest(...)         → 装载舱单检查
         └── calcAlerts()               → 预警计算（未运抵/未放行/未装/截港临近）
        │
        ▼
[接口层]  qingdaoController.js + routes ('/qingdao/*')
        │
        ▼
[前端层]  /qingdao 页（出口看板 + 预警中心）
        │
        ▼
[定时层]  qingdaoScheduler.js（每30分钟轮询在途订单）
```

> 关键原则：**先做"手动录入 + 规则推导"保证可用**，再接入场站/EDI 自动喂数。离开真实接口也能跑通闭环。

## 1. 数据模型层

### 1.1 新增模型 `QingdaoNode`
文件：`backend/src/models/QingdaoNode.js`

字段：
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增 |
| orderId | INTEGER NOT NULL | 关联订单 |
| bookingId | INTEGER | 关联订舱（可选） |
| node | ENUM(7节点) | picked_up/loaded/arrived_port/manifest_report/customs_release/loading_manifest/loaded_on_board |
| status | ENUM pending/done/warning/blocked | 节点状态（含红灯卡点） |
| eventTime | DATE | 节点发生时间 |
| detail | STRING(255) | 补充说明 |
| source | ENUM manual/api/edi | 数据来源 |
| operator | STRING(50) | 操作人 |

> 每订单每节点只有一条「最新状态」，用 `orderId+node` 唯一索引，更新采用 upsert。

### 1.2 扩展 `Order` / `Booking`
在 `Order` 增加青岛港字段：
| 字段 | 类型 | 说明 |
|------|------|------|
| terminal | STRING(20) | 码头 QQCT/QQCTU/QQCTN |
| openTime | DATE | 开港时间 |
| cutoffTime | DATE | 截港时间 |
| vesselName/voyageNo | 复用/冗余 | 方便看板免联查 |

### 1.3 注册模型与关联
- 在 `backend/src/models/index.js` 引入 `QingdaoNode`，加入导出。
- 关联：`QingdaoNode.belongsTo(Order)`、`Order.hasMany(QingdaoNode, { as: 'qingdaoNodes' })`。
- 数据库：开发 `sync({ alter })` 建表；生产走 migration。

### 1.4 验收
- 服务启动后 `QingdaoNode` 表自动创建。
- 可通过 `Order` 反查其青岛港节点。

## 2. 服务层 `backend/src/services/qingdaoService.js`

### 2.1 节点常量与状态推导
- 定义 7 节点顺序数组 `NODE_SEQ`，供看板渲染与预警计算。
- `statusOf(node, data)` 工具：根据数据源结果推导节点状态（done/warning/blocked）。

### 2.2 `getNodeBoard(orderId)`
- 查询该订单 `QingdaoNode` 全部节点 + `Booking`（船名/航次/截港）+ `CustomsDeclaration`（放行状态）+ `Order`（terminal/openTime/cutoffTime/containerNo）。
- 组装为一个 7 节点数组，每节点含 `{ node, label, status, eventTime, detail, source }`。
- 计算整体进度：已 done 节点数 / 7。

### 2.3 `updateNode(orderId, node, data)`
- upsert `QingdaoNode`。
- 支持 `source=manual`（前端手动标记）与 `source=api/edi`（自动喂数）。
- 记录 `operator` 与 `eventTime`。

### 2.4 `deriveFromSources(orderId)`（自动喂数，可选）
- 若已接场站查询（`/yards`）：`arrived_port` 由"进港"状态推导、`manifest_report` 由"运抵"推导。
- 若已接报关模块：`customs_release` 取报关放行状态。
- 若已接港口 EDI：`loading_manifest` 取装载舱单回执、`loaded_on_board` 取装船回执。
- 未接真实源时返回空，由 `updateNode` 手动补齐。

### 2.5 `checkManifest(bookingId)`（装载舱单检查）
- 输入：订舱/订单。
- 检查项与结果：
  | 检查 | 结果 |
  |------|------|
  | 报关单是否已放行 | 未放行 → blocked |
  | 预配舱单是否放行 | 未放行 → blocked |
  | 装载舱单是否已发送 | 未发送 → warning |
  | 是否已装船 | 已装 → done |
- 返回结构化检查结果，供前端展示"可装船"结论。

### 2.6 `calcAlerts()`（预警计算）
- 遍历"在途"订单（`Order.status in (confirmed,in_progress)` + 青岛港相关）。
- 规则引擎（数组化配置，便于扩展）：
  | 规则 | 触发条件 | 级别 |
  |------|----------|------|
  | 未进港且临近截港 | `now > cutoffTime - 6h` 且 `arrived_port != done` | warning |
  | 已进港未运抵 | `arrived_port=done` 且 `manifest_report != done` 超 2h | warning |
  | 已运抵未放行 | `manifest_report=done` 且 `customs_release != done` 超 2h | warning |
  | 放行未查装载舱单 | `customs_release=done` 且 `loading_manifest` 未确认 | warning |
  | 报关/舱单卡点 | `safe_release` 或 `loading_manifest` blocked | blocked |
- 返回预警列表 `[{ orderId, orderNo, containerNo, rule, level, message, dueAt }]`。

### 2.7 验收
- 对一条已知订单，`getNodeBoard` 返回 7 节点且状态正确。
- 构造"未进港临近截港"场景，`calcAlerts` 能命中。
- `checkManifest` 对"放行但装载舱单未发送"给出卡点提示。

## 3. 接口层 `backend/src/controllers/qingdaoController.js`

实现独立控制器（复用 `asyncHandler/ok/fail`），不套用通用 CRUD，因多为聚合/计算接口。

| 方法 | 路径 | 处理函数 | 说明 |
|------|------|----------|------|
| GET | /qingdao/nodes | nodes | 按 orderId 返回 7 节点看板 |
| POST | /qingdao/nodes | updateNode | 手动更新节点（source=manual） |
| GET | /qingdao/checklist | checklist | 返回 7 节点清单与顺序 |
| GET | /qingdao/alerts | alerts | 返回 `calcAlerts()` 结果 |
| GET | /qingdao/manifest/check | manifestCheck | 按 bookingId/orderId 检查装载舱单 |

### 3.1 路由注册
在 `backend/src/routes/index.js` 增加：
- `router.get('/qingdao/nodes', authRequired, qingdao.nodes)`
- `router.post('/qingdao/nodes', authRequired, qingdao.updateNode)`
- `router.get('/qingdao/checklist', authRequired, qingdao.checklist)`
- `router.get('/qingdao/alerts', authRequired, qingdao.alerts)`
- `router.get('/qingdao/manifest/check', authRequired, qingdao.manifestCheck)`

> 权限：先 `authRequired`，后续按《权限控制设计.md》补 `requirePermission('qingdao', 'read'/'update')`。

### 3.2 入参校验
- `nodes` 需 `orderId`。
- `updateNode` 需 `orderId`、`node`、`status`，校验 `node` 在 7 节点枚举内。
- 统一错误返回沿用 `fail(res, msg, 1, 400)`。

### 3.3 验收
- 调用 `/api/qingdao/nodes?orderId=1` 返回 7 节点结构。
- 调用 `/api/qingdao/alerts` 返回预警列表。
- 非法 node 入参被 400 拦截。

## 4. 前端层 `/qingdao` 页面

### 4.1 路由与菜单
- 新增 `frontend/src/views/qingdao/QingdaoPortal.vue`（或拆 `QingdaoBoard.vue` + `QingdaoAlerts.vue`）。
- 在 `frontend/src/router/index.js` 注册路由 `/qingdao`。
- 在侧边栏 `MainLayout.vue` 菜单加入"青岛港管理"，归属"运输跟踪"分组。

### 4.2 功能组件
- **出口看板**：输入/选择订单 → 调用 `GET /qingdao/nodes` → 渲染 7 节点时间线 + 状态灯（绿 done/黄 warning/红 blocked）。
- **预警中心**：调用 `GET /qingdao/alerts` → 表格展示，点击跳转对应订单详情。
- **节点操作**：看板上对未自动更新的节点提供"标记完成"按钮（`POST /qingdao/nodes`）。
- **装载舱单检查**：订单详情内按钮，调 `GET /qingdao/manifest/check` 展示可装船结论。

### 4.3 与订单详情联动
- 在现有 `OrderDetail.vue` 增加"青岛港节点"Tab，复用 `getNodeBoard`。
- 预警中心跳转回到订单详情并定位青岛节点。

### 4.4 验收
- `/qingdao` 页可展示订单 7 节点看板。
- 预警中心数据正确、可跳转。
- 手动标记节点后刷新状态灯更新。

## 5. 定时任务层 `backend/src/services/qingdaoScheduler.js`

### 5.1 定时轮询
- 每 30 分钟执行一次。
- 逻辑：查在途订单 → 对每个订单 `deriveFromSources`（若有源）→ 必要时 `updateNode` → 汇总 `calcAlerts`。
- 预警结果落库（或缓存），供 `GET /qingdao/alerts` 读取，避免每次实时计算。

### 5.2 接入方式
- 复用《控制性设计手册》的定时任务机制（如 `node-cron`）。
- 启动时注册一次，`server.js` 引入。

### 5.3 降级与限流
- 未接外部源时，定时任务仅做预警计算，不发起外部调用。
- 已接源时，限制单订单单周期调用次数，遵循缓存策略。

### 5.4 验收
- 定时任务可启动、可停止。
- 构造在途订单，定时任务能产出并持久化预警。

## 6. 实施顺序（建议分批提交）

| 批次 | 内容 | 依赖 |
|------|------|------|
| 批次 A | 模型层（QingdaoNode + Order 扩展 + 注册关联） | 无 |
| 批次 B | 服务层（getNodeBoard/updateNode/calcAlerts/checkManifest） | A |
| 批次 C | 接口 + 路由（/qingdao/*）+ 入参校验 | B |
| 批次 D | 前端 /qingdao 页 + 订单详情联动 | C |
| 批次 E | 定时任务 + 预警持久化 | B |
| 批次 F | 自动喂数（对接场站 /yards + 报关 + EDI） | E |

> 批次 A~E 不需要任何真实外部接口即可跑通"手动录入 + 规则预警"闭环；批次 F 再接入真实数据源增强自动化。
